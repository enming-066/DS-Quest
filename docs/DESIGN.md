# DS Quest 设计方案与实现说明

> 这份文档回答《DS_Quest_第一版项目方案》第八节列的 8 个问题，并记录**实际做出来的东西**与最初设想之间的差异、以及为什么这么改。
>
> 结论先行：**方案整体可行，已经按它做出了可用的第一版**（线性表 + 栈 + 队列，15 道判题、13 份代码模板、3 个可视化）。下面逐条说明。

---

## 1. 可行性分析与需求里潜在的问题

### 可行的部分

| 需求 | 判断 | 理由 |
| --- | --- | --- |
| 本地网页、单人使用 | 完全可行 | 不用处理多用户、权限、部署，复杂度下降一个量级 |
| Vue 3 + Vite + Monaco | 可行 | 都是成熟方案，Monaco 就是 VS Code 的编辑器 |
| FastAPI + SQLite | 可行 | 单人本地场景，SQLite 足够，也不用装数据库服务 |
| C++ 自动判题 | 可行，但有前提 | 需要本机有 g++；安全隔离是**真难点**（见第 7 节） |
| DeepSeek 接入 | 可行且便宜 | 被动调用 + 缓存 + 本地兜底，成本可以压到很低 |
| 数据结构可视化 | 可行 | 用 Vue + CSS 过渡就能做，不需要动画库 |

### 原需求里几个需要修正的地方

1. **"八个学习模块"和"第一版做三章"其实是矛盾的。**
   地图上写 8 关、内容只做 3 章，第一版会有一半的卡片点不了。
   → 做法：地图保留 8 关（未做的标"未解锁"并写明会讲什么），`modules.json` 里用 `status` 字段控制。这样地图的"闯关感"完整，又不会点进空页面。

2. **"栈"和"队列"在课程里是同一章。**
   方案里既说第三关叫「栈与队列」，又说第一版做"线性表/栈/队列"三个模块。
   → 做法：按课程走，第三关 = 栈与队列（8 个知识点、7 份代码、9 道题），地图上仍是 8 关。知识点用 `group` 字段分成"栈 / 队列"两小节。

3. **"AI 指出可能出错的代码位置"这件事，AI 并不可靠。**
   模型看不出 `for (i = 0; i <= n; i++)` 到底错没错——它不知道题目的数据范围。
   → 做法：把"定位错误"交给**事实**：判题会告诉你是第几个测试点、输入是什么、期望什么、你输出了什么。AI 只负责"解释为什么会这样"，并且提示词里明确要求"信息不足时先说明是推测"。

4. **安全执行 C++ 代码，在 Windows 上没有廉价又彻底的方案。**
   方案里写了"隔离运行、限制文件访问"，但没指定手段。
   → 做法：作业对象（内存/进程数/超时强杀）+ 独立临时目录 + 输出上限，够个人使用；同时在 README 里**明确写出边界**和升级路径（WSL2/Docker/低权限用户）。这是诚实工程，不是假装安全。

5. **"游戏化"很容易变成负担。**
   → 做法：只保留三样——XP、等级、通关状态。没有签到、没有排行榜、没有体力值。判题通过才给 XP，避免"刷经验"。

6. **"参考代码"和"答案"的边界要划清。**
   方案要求分层提示，但没定义"什么算剧透"。
   → 做法：提示分三层（方向 → 定位 → 参考思路），前两层来自题库、免费；完整参考解单独放在「题解」页，默认折叠，点开前有确认。

## 2. 第一版功能取舍

### 必须做（已完成）

- 学习地图 + 章节页 + 知识点页 + 代码库
- Monaco 编辑器 + 真实编译运行的判题
- 判题失败时给出**具体测试点对比**（这是"比 OJ 好用"的核心）
- 分层提示（免费）+ AI 助教（付费、被动）
- 本地错题本 + 进度记录
- 2~3 个可视化（实际做了 3 个）
- 内容自检脚本（保证题库数据不会自相矛盾）

### 延后（第一版不做）

| 功能 | 为什么延后 |
| --- | --- |
| 用户系统 / 云端同步 | 单人本地使用，SQLite 就够；加了反而增加心智负担 |
| 选择题 / 填空题 / 画图题 | 期末确实考，但题型交互和判分规则都要单独设计，先把编程题做扎实 |
| 完整 8 章内容 | 内容量是最大的成本，先做完两章跑通闭环，再按同样结构填 |
| 更严格的沙箱（Docker/WSL2） | 个人使用场景下收益低；架构上已经隔离在一个模块里，随时可替换 |
| 自定义输入运行（Playground） | 与判题区分开，属于第二个功能，第一版先不铺开 |
| 学习报告 / 遗忘曲线 | 数据已经在库里，等有几十道题再谈分析 |

## 3. 项目目录结构

完整版见 `README.md` 第三节。这里只解释**为什么这样分**：

```
backend/app/      业务代码，一个文件一件事
backend/content/  纯数据，和代码完全分离
frontend/src/     页面在 views，可复用块在 components
scripts/          一次性脚本，给"不想记命令"的人用
```

三个关键原则：

1. **内容与代码分离**：加题、改知识点只动 `content/`，不碰 Python/JS。以后把 PPT 里的题整理进来，就是新增 JSON 文件。
2. **代码模板正文放在 `.cpp` / `.c` 文件里**（不是塞在 JSON 字符串里）。这样你可以直接用 Dev-C++ 打开、编译、运行，也方便我以后改。
3. **依赖装在项目内**（`backend/vendor`、`frontend/node_modules`），不污染系统环境；换电脑只要重跑 `setup.bat`。

## 4. 前后端架构与通信

```
浏览器 (Vue 3 SPA)
   │  fetch /api/*
   ▼
FastAPI (127.0.0.1:8000)
   ├─ content.py   读 content/ 下的 Markdown + JSON（启动时加载进内存）
   ├─ judge.py     编译运行（g++ + Job Object）
   ├─ store.py     SQLite：进度 / 错题 / 提交记录 / AI 缓存
   ├─ ai.py        DeepSeek（urllib，无额外依赖）
   └─ 静态托管      frontend/dist
```

**为什么是一个端口**：生产模式下 FastAPI 直接托管 `frontend/dist`，你只需要记一个地址 `http://127.0.0.1:8000`。开发模式（`scripts/dev.ps1`）才拆成 5173 + 8000，由 Vite 代理 `/api`。

**接口一览**（`http://127.0.0.1:8000/docs` 有自动生成的文档）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/bootstrap` | 一次性拿到地图、进度、AI 额度、编译器状态 |
| GET | `/api/modules/{id}` | 章节详情（知识点正文、代码模板、题目列表） |
| GET | `/api/problems/{id}` | 题目详情（**不含隐藏测试数据**） |
| POST | `/api/judge` | 提交判题 |
| POST | `/api/ai/coach` | AI 助教（分层） |
| GET | `/api/ai/budget` | 今日 AI 用量 |
| POST | `/api/progress/knowledge` | 知识点打卡 |
| GET/POST | `/api/wrongbook*` | 错题本、笔记、标记掌握 |

**状态管理**：前端只用一个 `reactive` 对象（`src/store.js`）装地图/进度/额度，够用且不容易出同步 bug。页面自己负责自己的数据（章节、题目详情），不搞全局缓存。

## 5. 三个技术点分别怎么接

### 5.1 代码编辑器（Monaco）

- 用 `monaco-editor` npm 包，Vite 原生支持它的 worker（`?worker` 后缀导入）。
- 自定义了一套深色主题（`dsq-dark`），和代码库里的代码块视觉统一。
- **降级策略**：如果 Monaco 加载失败（比如依赖没装全），自动换成 `<textarea>`，判题功能不受影响。
- 快捷键：`Ctrl + Enter` 提交。
- 草稿自动存 `localStorage`，换页/刷新不丢代码。

### 5.2 判题系统

流程见 README 第五节。几个实现细节值得记下来：

- **编译参数按编译器版本自动选**：`g++ -dumpversion` 判断主版本，≥8 用 `-std=c++17`，5~7 用 `-std=c++14`。这台机器是 TDM-GCC 5.1，不支持结构化绑定，如果不做这个判断，学生会遇到"代码看起来没错却编译不过"的困惑。
- **`-static` 链接**：避免 MinGW 的 DLL 不在 PATH 里导致运行失败。
- **stdin/stdout 走文件而不是管道**：避免输出量大时死锁，也方便限制输出长度。
- **Job Object**：限制内存、进程数，`KILL_ON_JOB_CLOSE` 保证超时后整棵进程树被杀掉，不留僵尸。
- **只展示出错测试点**：全量展示等于给答案；只展示第一个失败点足够定位问题。
- **归一化比对**：忽略行尾空格和末尾空行，和主流 OJ 一致，避免"少一个换行就 WA"的挫败感。

### 5.3 DeepSeek AI 助教

- 用 `urllib` 直接调 HTTP，不引入 openai SDK（少一个依赖，也更容易看懂请求体）。
- **被动调用**：路由是 `POST /api/ai/coach`，只有前端点按钮才会发。
- **分层**：`level` 2/3/4 对应"给方向 / 定位问题 / 参考思路"，提示词不同。level 4 如果题库有参考解，**直接本地返回，不发请求**。
- **省钱三件套**：SHA256 缓存（题 + 代码 + 问题 + 模型）、每日额度（默认 30）、`max_tokens` 限制。
- **教学意识**：系统提示词里写死"不要给完整可运行程序""必须引用具体变量名""回答控制在 350 字"，并要求固定三段式结构（我的判断 / 你应该先检查 / 原理提示）。
- **Key 不落前端**：只从 `backend/.env` 读，接口不返回 Key，也不写入数据库。

## 7. 难点评估

### 7.1 C++ 代码安全执行（最难，且没有完美解）

- **真问题**：用户代码可以 `while(1)`、可以 `system("shutdown")`、可以写文件、可以占满内存。
- **已做**：超时强杀、内存上限、进程数上限、独立临时目录、输出上限。
- **没做**：网络隔离、文件系统隔离、权限降级。
- **判断**：单机、单人、自己写自己跑，风险可接受。**一旦要开放给别人，必须换成 WSL2/Docker/低权限账户**——这是设计约束，不是实现遗漏。
- **升级成本**：`judge.py` 里 `run_program()` 一个函数就能替换，其余代码不用动。

### 7.2 自动判题的正确性（第二大坑）

判题本身的代码不长，**难在题库数据容易自相矛盾**：样例写错了、标准答案算错了、边界没覆盖。
→ 对策：`verify.py` 用参考解真跑一遍所有测试点。写内容时它就抓出了两道题的标准答案错误（`ll-02` 的样例、`st-02` 的一个边界）。这个脚本是整个项目最值钱的部分之一。

### 7.3 AI 错误分析（最容易被高估）

- 模型**不能**替代编译器，也不能可靠地判断算法对错。
- 它能做好的：解释编译错误、把"输出对不上"翻译成"你可能漏了最后一行/多了一个空格"、把错误和课本概念连起来。
- 设计上把 AI 放在**最后**：先看编译器、再看测试点、再看免费启发式检查，都不够才问 AI。

### 7.4 内容生产成本（真正的瓶颈）

写一道好题（题面 + 样例 + 5 个测试点 + 参考解 + 3 层提示）大约 15~25 分钟。
15 道题就是 5 个小时的活。这也是为什么第一版只做两章——**先把结构跑通，再批量填内容**。

### 7.5 可视化与"游戏感"的度

做多了会变成玩具。原则：**每个可视化只解释一个考点**（顺序表的挪动方向、栈的 LIFO、循环队列的取模），带逐步播放，不做粒子特效。

## 8. 第一阶段具体实施步骤（已完成）

1. 建目录：`backend/` `frontend/` `scripts/`。
2. 后端骨架：`config.py`（配置）→ `content.py`（加载 Markdown/JSON）→ `store.py`（SQLite）→ `judge.py`（判题）→ `ai.py` → `main.py`（路由）。
3. 内容骨架：`modules.json` + `linear-list/module.json` + 第一个知识点，先让接口有数据。
4. 前端骨架：Vite + Vue + Router，`App.vue`（顶栏）+ `MapView`，把地图跑起来。
5. 联调：`api.js` 对接 `/api/bootstrap`，确认跨端口 CORS 和代理正常。
6. 再补内容、再补页面，用 `verify.py` 和 `smoke_test.py` 卡质量。
7. 打包：`vite build` → FastAPI 托管 → 单端口访问 → 写启动脚本。

**给初学者的一点建议**：这套代码刻意用了最"笨"的写法——没有状态管理库、没有 TypeScript、没有 ORM、没有 Docker。每个文件都能从头读到尾。等你熟悉了再换更工程化的方案，不要一开始就被工具链劝退。
